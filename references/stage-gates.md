# 阶段门判据与排查顺序

每道门都设计成**能机械判定**：能跑脚本就别靠眼睛，能反抽下游产物就别只查源文件。

每条都给了「判据不通过时先查什么」的顺序 —— **这个顺序比判据本身更重要**，因为它的作用是防止你从一个错误的假设开始查。

---

## 门 0 · 规格冻结与可测性

**判据**

```
功能清单  N 行，每行三列：功能 / 怎么测 / 测不出来怎么办
「怎么测」空项数 = 0
「测不出来怎么办」空项数 = 0
资源预算表：功能数 = 预算行数
```

**不通过先查什么**

1. 有没有哪一行写着"看波形对不对"——这不是测法，是主观判断。改成可量化量（频率读数 / 峰峰值 / 峰位 bin）。
2. 有没有哪一行只能靠人眼在 GUI 里看——GUI 崩溃时你就无法验证（这个项目的 GUI 崩溃是常态）。
3. 预算表是不是直接从"我觉得能放下"来的。哪怕粗估，也要写下每项的依据（参考同类实现 / 数据手册 / 别人案例）。

**为什么这道门在最前面**

时基四档做完以后，实机切换 T3/T4 无响应、根因未定位，最后只能把上位机与工具全部撤除，只开放两档。

**如果第 0 周就写了"T3/T4 怎么测：设 6.25MHz 时基，看频谱横轴是否变成 0~3.125MHz"，这个功能不会带着问题活到交付前。**

## 门 1 · Python 整数金标准

**判据**

```
模型能输出与 RTL 逐位相同的结果（不是"误差在范围内"）
模型能复现板上至少一个已知错误现象
```

第二条是关键。**只能对上"正确结果"的模型，抓不到真实现象。**

**不通过先查什么**

1. 定点口径是否一致：位宽、右移位数、饱和还是截断、Q 格式。
2. 取模方式是否一致：L1（`|re|+|im|`）vs 平方和开方 —— 两者差 10% 以上，混用就永远对不上。
3. 测试数据是不是合成信号。**必须用真实采样回灌**，合成信号里没有量化杂散和直流偏置。

**为什么值得先花时间**

自研 FFT 的 502 LUT 之所以敢说"正确"，不是因为它比 IP 小，而是因为三个峰位与整数模型逐字一致。这等于给自研核配了一个可独立复算的参照物。

反过来，第三峰在基频 5kHz 后折叠成"看起来很合理的错值"，也是靠模型确认这是真实现象、不是 bug。

## 门 2 · 分模块上板

**判据**

```
每加一块 → 跑一次资源检查（门 3 的方法）
增量 vs 预估偏差 ≤ 30%
WNS > 0 且 failing endpoints = 0
新增模块至少有一个不依赖 UI 的可观察量
```

**不通过先查什么**

1. **增量远大于预估** → 先怀疑存储体推断失败（门 3 第一步）。
2. **增量远小于预估** → 先怀疑该模块根本没被综合进去（端口漏接、被优化掉）。
3. 时序突然恶化 → 查是不是新增了一条长组合路径（比较器链、大扇出）。

**"独立可观察量"是硬要求**

两个功能代码写了、协议里有、上位机有按钮，实测完全没反应 —— 因为指令译码实例化漏接两个端口，Verilog 把未连接输入当无驱动网络，**综合器一句警告都没有**。

发现它靠的是逐条发命令看回报变化。如果每个模块都有这么一个可观察量，这类问题活不过一天。

## 门 3 · 资源与时序判读

**判据**

| 检查项 | 通过条件 |
|---|---|
| 数据来源 | 文件名含 `_placed.rpt` / `_routed.rpt`，**不是**综合报告 |
| 存储体 | 按实例名查到 `RAMB36E1`/`RAMB18E1`，不是 `FDRE` |
| LUT 余量 | ≤ 85% |
| 时序 | WNS > 0 **且** failing endpoints = 0 |

**排查顺序（不要跳）**

```
① 先确认看的是实现报告
    综合报告把 OOC IP 当黑盒，总数偏小。真实例子：
    综合 6087 → 层次 8587 → 实现 7358/7886，三份口径全不一样。
② 再看存储体原语
    按「实例名 + 原语类型」查。写 ram_style="block" 只是愿望，
    读口带异步复位就推断失败 → 32768 位全铺 FDRE → 单项吃 86% LUT。
③ 再看 DSP
    乘法器是否被推断成 DSP48，还是退化成 LUT 里的移位加法。
④ 最后看时序
    routed 报告，WNS/WHS/WPWS + 失败端点数。
```

**为什么顺序不能反**

先看总数会得到"资源超了"的结论，然后你会去砍功能。**但真正的问题可能是一个存储体用了 86% 的 LUT。** 砍掉三个功能也救不回来。

**常见误判**

- 拿历史报告对比。改完不看"我改的那一个东西变了没有"，被总数掩盖 —— 这个项目曾有一个从未生效的"修复"，藏了 25 天。
- 忘了调试核（ILA 之类）还开着。它可能占 3.5% LUT 和大量布线，开与关是两套数字，而且是两套时序。

## 门 4 · 模拟链路标定

**判据**

```
换算系数 = 具体数字 + 单位，写在文档里
系数已固化为 RTL 常量（不是只在主机侧算）
有明确的重标定触发器（例：动了某电位器必须重标）
```

**排查顺序**

1. 真值测量器具本身准不准（这个项目万用表坏过，靠借）。
2. 输入量程与内部偏置 —— 模块输入端 vs ADC 端可能差好几倍，**要写清显示的是哪一端**。
3. 系数是否只在主机侧用。板上和主机两套值会互相矛盾。

## 门 5 · 协议口径审计

**判据**

```
① 存在命令号分配表，且是唯一事实源
② 帧格式全库统一（帧头 / 长度 / 校验和起算位置）
③ 审计脚本覆盖上行帧 + 下行帧
④ 静默命令（不回 ACK）逐个列出
⑤ 每条命令在"分配表 / RTL / 文档"三处都存在
```

**排查顺序**

1. **先查校验和起算位置**。这一类错误最隐蔽，因为它不影响发送方，只让接收方静默丢弃。
2. 再查命令号是否撞号。
3. 最后查静默命令的"可观察量"是否写清。

**真实案例（代价最大的一条）**

锁相帧校验和从 `body[0]` 起算、含帧头 `5A A5`；波形帧与谱帧从 TYPE 起算。
`5A + A5 = 0xFF ≡ −1` ⇒ 发出的校验和**永远小 1** ⇒ 上位机每帧判失败并**静默丢弃**。

结果：**从界面诞生起，锁相读数一次都没显示过。** 而另一组 −18.8dB 数据是真的（用另一个按帧头找、不做校验的脚本测的）—— 「数据真、界面假」共存了很久。

由此三条铁律：

1. 多帧类型共存时校验和口径必须统一，**上行帧必须进审计器**。
2. **解析失败要吵闹，不能静默丢弃** —— 「不显示」和「算错了」在用户眼里是同一件事。
3. **界面类功能必须端到端验证一次**，不能只测"脚本能读到数据"。

## 门 6 · 文档三处同步

**判据**

```
从生成的 PDF 反抽文字扫描：过期值命中 0，禁项命中 0
README / PDF / 讲稿三处数字一致
含照片的页已人眼过一遍
```

**排查顺序**

1. **PDF 是不是最新的**。源文件改对但 PDF 没重建，等于没改。真实情况：滞后 4 天。
2. 从 PDF 反抽文字扫，**不要扫源文件**。评委看的是 PDF。
3. 扫"图里的字" —— 文本扫描查不出来，只能人眼看。真实案例：实物照片背景出现学院名和书院名（不是学校名，但足以定位）。
4. 区分「当前状态」和「历史记录」。

**"历史记录"怎么处理**

- 描述**当前状态**的 → 改成真实值
- 带**明确日期**的历史记录（当时的测试报告、日志）→ **保留原值**，加一条横幅指向当前值

一刀切全改会毁掉证据链，比不改更糟。

## 门 7 · 打包与比对

**判据**

```
缺 0 ｜ 多 0 ｜ md5 差异 0
顶层目录唯一（不套娃）
```

**排查顺序**

1. **先看工作区是否干净**（`git status`）。不干净说明打包后还改过代码。
2. **解压出来逐文件 md5 比对**，不要只看时间戳。时间戳新不代表内容新，反之亦然。
3. 检查有没有嵌套的旧仓库（这个项目里有一个 9 月建的旧空壳克隆，排除法容易漏）。

**顺序铁律**

```
提交所有代码 → 打包 → 打完后不要再动代码
```

真实踩过两次：提交完新工具后仓库变成 379 个文件，而包还是 378 —— **一提交工具，包立刻过期**。

**为什么用白名单不用排除法**

排除法（排除 `.git`、排除 runs 目录…）容易漏。白名单明确列出"要哪些"，漏了就少文件，能立刻发现。

## 门 8 · 视频与演示材料

**判据**

| 项 | 判据 |
|---|---|
| 音轨对齐 | 音轨时长 ≈ 视频时长（±0.5s）|
| 字幕完整 | 字幕条数 × 平均字数 ≈ 旁白总字数 |
| 字幕合并处 | 不出现"连读掉标点"（"两千零一插值" 应为 "两千零一，插值"）|
| 卡片排版 | 渲染后查边框外深色像素 = 0 |
| 卡片底部 | 最低文字行与底栏余量 > 50px |

**排查顺序（时长对不上时）**

```
① 全局包络互相关，求时间偏移
    偏移 0.0s + 相关 > 0.8  → 同一套旁白，问题在编辑/编码
    偏移明显非 0           → 确实换了旁白或删加了段落
② 分段互相关（按段落切）
    全部 > 0.7  → 确认无段落替换
    某段 < 0.45 → 那一段被换了，定位成功
③ 单独查"最可能被替换的那一段"
④ x=0 结论
```

真实案例：成片比模板长 1.3 秒。全局相关 0.833、偏移 0.0；分段全部 0.84~0.955；连最可能被替换的那一段也有 0.877。**结论：编辑差异，不是旁白版本差异 —— 省掉整条视频重录。**

**TTS 必须缓存**

按 `hash(voice, rate, text)` 缓存音频与词边界。改卡片、改图、改标题都不动旁白，不该重新合成。断网时这条能救命。

## 门 9 · 交付前终审

**判据**

```
三个脚本 exit code 全 0
人工过一遍所有含照片的页
```

```bash
python scripts/check_deliverables.py  <交付目录> --required required.json
python scripts/audit_stale_numbers.py <仓库根>   --map stale_map.json
python scripts/check_pdf_text.py      <技术文档.pdf> --banned banned.txt --stale stale.txt
```

**这道门查不出来的东西（必须人工）**

- 照片背景里的文字
- 图内嵌字
- 版式问题（图被裁、文字压图）
- 演示现场的实际表现
- 评委的主观印象

**报告里必须写明"未覆盖项"**，不要让人以为全绿就等于万事大吉。
